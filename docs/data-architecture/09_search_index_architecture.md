# 09. Search & Indexing Architecture
## AI Brand Intelligence & Visibility Platform

This search and indexing architecture defines how the platform structures, indexes, and queries databases to support high-throughput analytical queries, full-text search, vector retrieval, and hybrid search pipelines.

---

## 9.1 Multi-Model Search Indexes

Our search systems employ four types of database indexing strategies:

```
+-----------------------------------------------------------------------------------------+
|                                    SEARCH INDEX ENGINE                                  |
+-----------------------------------------------------------------------------------------+
|                                                                                         |
|   1. B-Tree Indexes (PostgreSQL)  ===> Matches workspace_id, project_id, user keys.     |
|   2. Full-Text Search (Gin/Tsvec) ===> Keyword matching, search query text matching.     |
|   3. Vector Search (Pinecone/HNSW)===> Semantic retrieval matching (1536-dim embeddings)|
|   4. Hybrid Search Pipeline       ===> Blends keyword exact-match with vector semantics.|
|                                                                                         |
+-----------------------------------------------------------------------------------------+
```

---

## 9.2 Relational PostgreSQL Indexing (B-Tree & Hash)
To guarantee microsecond response times inside transactional and workspace dashboards, we implement targeted indexes on our relational database:

*   **Primary Keys & Foreign References**: Every UUID PK and FK is B-Tree indexed automatically.
*   **Tenant Partition Indexes**: Multi-tenant isolation queries verify `workspace_id` and `project_id`. Composite B-Tree indexes are created to optimize these common query patterns:
    *   `CREATE INDEX idx_workspaces_org ON workspaces(org_id);`
    *   `CREATE INDEX idx_projects_workspace ON brand_projects(workspace_id);`
    *   `CREATE INDEX idx_prompts_project ON prompts(project_id) WHERE is_active = TRUE;`
*   **Time-Series Partition Indexes**: Scraped observations are indexed chronologically to speed up chart rendering and weekly calculations:
    *   `CREATE INDEX idx_responses_created ON ai_responses(created_at DESC);`
    *   `CREATE INDEX idx_mentions_response ON brand_mentions(response_id);`

---

## 9.3 Full-Text Search (FTS) Indexing
For standard text search (e.g., users searching through generated AI transcripts or log files in the dashboard), we leverage PostgreSQL's native Full-Text Search (FTS) engines:

*   **Indexing Method**: GIN (Generalized Inverted Index) on `tsvector` columns.
*   **Multilingual Support**: To support bilingual search across our primary markets, we configure distinct linguistic dictionaries inside PostgreSQL:
    *   English language fields use the default standard `english` parser.
    *   Persian fields use the custom `persian` stemmer extension (such as the `plp` Persian Language Processing package) to handle zero-width non-joiners (half-spaces) and character normalization rules.
*   **Example FTS Index**:
    `CREATE INDEX idx_responses_text_fts ON ai_responses USING gin(to_tsvector('english', raw_response_text));`

---

## 9.4 Vector Search Indexing (Semantic)
For GEO audits and RAG simulation features, we store high-dimensional semantic vectors (e.g., 1536-dimension vectors generated by OpenAI's `text-embedding-3-small` or regional models):

*   **Indexing Algorithm**: HNSW (Hierarchical Navigable Small World) with Cosine Distance metrics inside our Vector DB (Pinecone or pgvector).
*   **HNSW Configuration**:
    *   `m`: 16 (Max number of bidirectional link connections per node).
    *   `ef_construction`: 64 (Construct probe depth, balancing build latency with recall precision).
*   **Query Metric**: Cosine similarity measurements:
    $$\text{Cosine Similarity} = \frac{\mathbf{A} \cdot \mathbf{B}}{\|\mathbf{A}\| \|\mathbf{B}\|}$$

## 9.5 Hybrid Search Pipeline (Lexical + Semantic)
To provide maximum recall precision during GEO audits, our search pipeline uses a hybrid search strategy that combines lexical exact-matching with semantic vector retrieval:

```
                  +--------------------------------------+
                  |      User Search Query Input         |
                  +------------------+-------------------+
                                     |
             +-----------------------+-----------------------+
             |                                               |
             v                                               v
+----------------------------+                  +----------------------------+
| Lexical Path (FTS GIN)     |                  | Semantic Path (HNSW Vector)|
| - Finds exact product SKUs |                  | - Catches conceptual intent|
| - Finds brand names        |                  | - Handles spelling variations|
+------------+---------------+                  +------------+---------------+
             |                                               |
             +-----------------------+-----------------------+
                                     |
                                     v
                  +--------------------------------------+
                  |   Reciprocal Rank Fusion (RRF)       |
                  |   - Merges and re-ranks top results  |
                  +------------------+-------------------+
                                     |
                                     v
                  +--------------------------------------+
                  |  Optimized Final Analytical Result   |
                  +--------------------------------------+
```

### 9.5.1 Reciprocal Rank Fusion (RRF) Ranking Logic
Our pipeline merges lexical and semantic search results using a standard Reciprocal Rank Fusion (RRF) algorithm:
$$\text{RRF Score}(d) = \sum_{m \in M} \frac{1}{k + r_m(d)}$$
Where $M$ is the set of search pathways, $r_m(d)$ is the rank of document $d$ within pathway $m$, and $k$ is a constant stabilizer (typically set to 60). This hybrid scoring pipeline ensures that technical references (like direct product SKUs) and conceptual topics (like user search intent) are weighted fairly in our analyses.
